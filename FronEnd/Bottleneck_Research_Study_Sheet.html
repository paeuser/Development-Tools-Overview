🔎 Researching Bottlenecks (Angular + SQL Server)

[ Angular (Frontend) ] ---> [ API / Backend ] ---> [ SQL Server (Database) ] | | | Tools: DevTools, Tools: Logging, APM Tools: Profiler, Lighthouse, Network Tab (App Insights, etc.) Query Store, Execution Plans

1️⃣ Angular (Frontend)

  • Where issues show: Slow load, large bundle, redundant API calls, laggy rendering.
  • Tools: Lighthouse (First Contentful Paint, Time to Interactive), Network Tab (TTFB, waterfall, parallel calls).
  • Optimizations: Lazy loading, bundle size analysis (ng build --stats-json), trackBy in *ngFor.

2️⃣ API / Backend

  • Where issues show: Slow endpoints, inefficient logic, missing caching.
  • Tools: Logging elapsed times, APM tools (Application Insights, New Relic, Dynatrace).
  • Checks: Endpoint response times, CPU/memory usage, caching strategy.

3️⃣ SQL Server (Database)

  • Where issues show: Slow queries, missing indexes, locking/blocking.
  • Tools: SQL Profiler, Extended Events, Query Store, Execution Plans, DMVs.
  • Optimizations: Add indexes, update statistics, tune joins, optimize stored procs.

🚀 Example Interview Summary

“I research bottlenecks across the whole stack. On the Angular side, I start with Chrome DevTools and Lighthouse to measure load times and API call efficiency. If APIs are slow, I trace them with logging or APM tools to check backend performance. If backend points to SQL, I profile queries with Query Store and execution plans. This lets me pinpoint whether the bottleneck is frontend rendering, API logic, or database performance.”
