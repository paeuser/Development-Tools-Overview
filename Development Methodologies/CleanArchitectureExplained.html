Clean Architecture Explained

Clean Architecture is a software design philosophy introduced by Robert C. Martin (Uncle Bob). It emphasizes separation of concerns, making software easier to maintain, test, and scale.

Core Principles

  • Independence of Frameworks: Architecture does not depend on any particular framework.
  • Testability: Business rules can be tested without UI, database, or external devices.
  • UI-agnostic: The UI can change easily without changing the rest of the system.
  • Independent of Database: The system can work with any database or none at all.
  • Independent of External Agencies: Business rules are not affected by external factors.

Layered Structure

1. Entities

Enterprise-wide business rules. These are the core objects of the system and contain the most general and high-level rules.

2. Use Cases (Application Layer)

Application-specific business rules that orchestrate the flow of data to and from the entities, implementing the business logic.

3. Interface Adapters

Convert data from the format most convenient for the use cases and entities to the format convenient for external agencies such as the database or the web.

4. Frameworks & Drivers

Details like UI, database, frameworks, and other external tools. This is the outermost layer and can be changed without affecting the inner layers.

Dependency Rule

Source code dependencies must point inward, toward higher-level policies. Inner layers should not know anything about outer layers.

Summary

Clean Architecture promotes building software with clear separation between business rules and external concerns. This leads to flexible, maintainable, and testable software systems.

Where to Place CQRS and MediatR in Clean Architecture?

1. CQRS (Command Query Responsibility Segregation)

Category: Typically fits in the Use Cases (Application Layer)

Why?
CQRS separates commands (write operations) from queries (read operations), focusing on how business logic is executed and data is accessed. Since it deals with orchestrating business rules and application workflows, it lives in the Application Layer.

What it does:
It structures the application by splitting the write and read concerns, often improving scalability and clarity in business logic implementation.

2. MediatR

Category: Primarily an Interface Adapter / Application Layer helper

Why?
MediatR is a mediator pattern implementation for .NET, used to decouple the sender and receiver of requests. It helps to handle commands, queries, and notifications without tight coupling.

How it fits:
It acts as a message dispatcher inside the Application Layer, routing commands and queries to handlers.

Sometimes considered part of the Interface Adapters because it adapts requests between UI or API layers and the core business logic.

Summary Table
Concept Clean Architecture Layer Role
CQRS Use Cases (Application Layer) Organizes commands and queries (business rules orchestration)
MediatR Application Layer / Interface Adapters Handles message routing between layers (decoupling components)

Extra Tip

CQRS is a pattern for separating reads and writes in your application, improving clarity and scalability.

MediatR is a library/tool that implements messaging between parts of your app, often used to organize CQRS handlers and decouple components.

Step 1: Simple Business Case

Business Case:
You want to build a simple app where users can add tasks to a to-do list and also get the list of tasks.

  • Users can add a task (write operation).
  • Users can view tasks (read operation).

This is a classic example for CQRS:

  • Adding a task is a Command (it changes data).
  • Getting tasks is a Query (it just reads data).

Step 2: Write Operation – Adding a Task (Command)

  • Scenario: A user wants to add a new task.
  • The UI sends a request with task details (e.g., title).
  • This request is represented as an AddTaskCommand.
  • MediatR receives the command and dispatches it to an AddTaskCommandHandler.
  • The handler executes business logic to create and save the new task.
  • The handler uses a repository interface (e.g., ITaskRepository) to persist the task (database, memory, etc.).
  • The handler returns a result, such as the new task's ID or a success message.

// 1. The Command
public record AddTaskCommand(string Title) : IRequest<int>;

// 2. The Command Handler
public class AddTaskCommandHandler : IRequestHandler<AddTaskCommand, int>
{
    private readonly ITaskRepository _repository;

    public AddTaskCommandHandler(ITaskRepository repository)
    {
        _repository = repository;
    }

    public async Task<int> Handle(AddTaskCommand request, CancellationToken cancellationToken)
    {
        var task = new TaskItem { Title = request.Title };
        await _repository.AddTaskAsync(task);
        return task.Id;  // Return new task's ID
    }
}

// 3. Repository Interface
public interface ITaskRepository
{
    Task AddTaskAsync(TaskItem task);
}

// 4. Task entity
public class TaskItem
{
    public int Id { get; set; }
    public string Title { get; set; }
}

Step 3: Read Operation – Getting Tasks (Query)

  • Scenario: A user wants to view their tasks.
  • The UI sends a request to get the list of tasks.
  • This request is represented as a GetTasksQuery.
  • MediatR receives the query and dispatches it to a GetTasksQueryHandler.
  • The handler uses the repository interface (ITaskRepository) to fetch the list of tasks from storage.
  • The handler returns the list of tasks to the user.

Why is this part of Clean Architecture?
The query and query handler live in the Application Layer, keeping business rules separate from UI or database.
The repository interface hides the storage details.
MediatR keeps the query sender and handler decoupled, improving maintainability.

Simple example in code (C# style):


// 1. The Query
public record GetTasksQuery() : IRequest<List<TaskItem>>;

// 2. The Query Handler
public class GetTasksQueryHandler : IRequestHandler<GetTasksQuery, List<TaskItem>>
{
    private readonly ITaskRepository _repository;

    public GetTasksQueryHandler(ITaskRepository repository)
    {
        _repository = repository;
    }

    public async Task<List<TaskItem>> Handle(GetTasksQuery request, CancellationToken cancellationToken)
    {
        return await _repository.GetTasksAsync();
    }
}

// 3. Update Repository Interface to include GetTasks
public interface ITaskRepository
{
    Task AddTaskAsync(TaskItem task);
    Task<List<TaskItem>> GetTasksAsync();
}
