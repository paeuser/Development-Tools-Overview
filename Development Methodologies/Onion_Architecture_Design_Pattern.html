🧅 Onion Architecture

A Clean, Maintainable Software Design Pattern

What is Onion Architecture?

Onion Architecture is a software design pattern that organizes your code into concentric layers, just like an onion! Each layer has a specific responsibility and can only depend on layers closer to the center. This creates a clean, maintainable, and testable codebase.

Onion Architecture Layers Explained

  1. Domain Layer (Core / Center of the Onion)
    • What it contains: Entities (business models), domain services, business rules.
    • Purpose: Represents the pure business logic without dependencies on other layers.
    • Key point: This layer should not depend on any external frameworks or libraries.
  2. Application Layer (Use Cases)
    • What it contains: Application services, use case logic, DTOs (data transfer objects), interfaces for persistence or external services.
    • Purpose: Defines how the business logic is used (use cases), orchestrates workflow.
    • Key point: Depends only on the Domain Layer. No infrastructure details here — only contracts/interfaces.
  3. Infrastructure Layer
    • What it contains: Implementation details (repositories, data access, EF Core, logging, email providers, external APIs).
    • Purpose: Provides concrete implementations for the interfaces defined in the Application Layer.
    • Key point: This depends on the Application Layer, not the other way around.
  4. Presentation Layer (UI / API / Outer Layer)
    • What it contains: Web API controllers, UI (MVC, Angular, React, etc.), CLI, REST endpoints, GraphQL, etc.
    • Purpose: Handles user interaction or external input/output.
    • Key point: Calls into the Application Layer to perform operations. It should not contain business rules.

📌 The Dependency Rule

Code dependencies always point inward.

Outer layers know about inner layers, but inner layers don’t know about outer ones.

Example: UI → Application → Domain.

Infrastructure is plugged in at runtime (e.g., repository implementations injected via dependency injection).

Key Benefits

🔧 Easy to Test

Each layer can be tested independently. Mock external dependencies easily and focus on testing business logic.

🔄 Flexible & Adaptable

Change databases, UI frameworks, or external services without affecting your core business logic.

📚 Clear Separation

Each layer has a single responsibility, making code easier to understand and maintain.

🎯 Focus on Business Logic

Your core domain logic stays pure and independent of external concerns.

Simple Code Example

Here's how you might structure a simple e-commerce application:

// Domain Core (Center of the onion)
class Product {
    constructor(name, price) {
        this.name = name;
        this.price = price;
    }
    
    calculateDiscount(percentage) {
        return this.price * (percentage / 100);
    }
}

// Application Services Layer
class ProductService {
    constructor(productRepository) {
        this.productRepository = productRepository;
    }
    
    async createProduct(name, price) {
        const product = new Product(name, price);
        return await this.productRepository.save(product);
    }
}

// Infrastructure Layer
class DatabaseProductRepository {
    async save(product) {
        // Save to database
        return product;
    }
}

// Presentation Layer
class ProductController {
    constructor(productService) {
        this.productService = productService;
    }
    
    async createProduct(req, res) {
        const product = await this.productService.createProduct(
            req.body.name, 
            req.body.price
        );
        res.json(product);
    }
}

Traditional vs Onion Architecture

❌ Traditional Layered

Problems:

  • Tight coupling to databases
  • Hard to test business logic
  • Changes ripple through layers
  • Business logic mixed with infrastructure

✅ Onion Architecture

Solutions:

  • Business logic is independent
  • Easy to swap implementations
  • Highly testable
  • Clear dependency direction

The Golden Rule

"Dependencies always point INWARD"

Outer layers can depend on inner layers, but inner layers should never depend on outer layers. This keeps your core business logic pure and independent.

When to Use Onion Architecture

Great for:

  • Complex business applications
  • Long-term projects that need maintenance
  • Applications with changing requirements
  • Projects that need extensive testing

Maybe overkill for:

  • Simple CRUD applications
  • Prototypes or proof-of-concepts
  • Very small projects with simple logic
